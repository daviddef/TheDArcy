Hi Liz,

Thanks for coming back to me. Answers to your four questions, in order.

**1. The existing applications and research tools that will access Trove data.**

There is one, and it is small. I keep a public family-history archive at
https://daviddef.github.io/TheDArcy/, with its source at
https://github.com/daviddef/TheDArcy. It is a static website — no server, no
database, no user accounts. It is built with Astro (a JavaScript static-site
generator) and about twenty short Python scripts that fetch data, check it and
turn it into pages.

The script that would use the Trove API does not exist yet. It would be one more
of those: roughly fifty lines of Python using the standard library, calling
`/v3/result`, writing the response to a JSON file in the repository. I have
written the same thing this week against The National Archives' Discovery API
(`tools/discovery.py` in that repository), and the Trove one would be its twin.

**2. Will it incorporate AI components, and how would Trove data be used with AI?**

Yes, and I would rather be precise than brief about it.

I use Anthropic's Claude, through the Claude Code command-line tool, as an
assistant: it writes and debugs the Python, drafts prose, and checks the site's
internal consistency. So an AI system would read the Trove metadata the script
retrieves, in the same way it reads everything else in the repository, and would
help me write the page that presents it.

What it would **not** do, and what I am happy to have written into any agreement:

- No Trove content would be used to train, fine-tune or evaluate any model.
- No full text of any article would be retrieved. The request is metadata only —
  newspaper and gazette titles, their place coverage and their date ranges.
- Nothing generated by an AI would be published as though it were a Trove record.
  The archive grades every claim it makes by how well it is evidenced, publishes
  a page of its own corrections, and would cite Trove as the source of a title
  and a date range and nothing more.
- The archive's build refuses to complete if a published claim loses its source.
  That check is mechanical, not editorial.

**3. Will it be shared, and freely?**

Yes to both. The site is public and free, with no advertising, no tracking and
no paywall. The source code, including the script that would call your API, is
public on GitHub. The derived data — a table of which papers cover which places
in which years — would be published as an open JSON file, so anyone else's
research could use it without asking you for a key of their own.

**4. Why the API rather than the Trove website.**

Because I am trying to publish absences as well as findings, and the website
cannot support that.

A large part of this archive is statements of the form "this was searched for
and not found." Such a statement is only worth anything if the search can be
stated exactly, repeated identically across many spellings of a name, and tested
against a control that could have failed. A search box gives none of those: it
gives an answer with no record of the question.

A concrete example from two days ago. This archive had published that a
fourteenth-century document could not be found in The National Archives'
catalogue. Re-running that search through Discovery's API showed the record had
been there all along — the earlier search had used the wrong phrase. The
catalogue had not failed; the query had, and only a repeatable query could show
the difference.

What I want from Trove is narrow and dull: for each newspaper and gazette title,
the places it covers and the years it runs. Perhaps a few hundred rows, fetched
once and refreshed rarely. Then when this archive says "nothing was found in the
Queensland papers for 1849," the page can also say which papers existed, which
were digitised, and for which years — so a reader can tell the difference between
a silence and a gap.

I can do that against the API in an afternoon and it would be correct. Clicking
through the website I could approximate it, and I would have no way to show
anyone that I had done it consistently.
